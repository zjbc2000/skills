# 节俭全栈：低成本基础设施

## 何时使用
- 你要从 0 搭建一个全栈应用，且前期预算近乎为零。
- 你要选部署/数据库/认证/存储的免费方案，或判断"用 Firebase 还是 Supabase"。
- 你要给应用配域名、上 HTTPS、接 CI/CD。
- 你要理解各工具在技术栈里的角色（用"餐厅模型"理清前后端/API/数据库分工）。

## 核心规则

1. **用"餐厅运营模型"理解全栈分工**：前端=大堂（用户所见），后端=厨房（业务逻辑），数据库=仓库（食材/数据），API=服务员（传达订单与反馈）。选工具时先想清楚它在"餐厅"里的角色。来源：第3章

2. **优先选"开源"免于供应商锁定**：Supabase 是 Firebase 的开源替代（BaaS），基于 PostgreSQL；开源意味着透明、可改造、可自托管搬迁，拥有"数字资产所有权"。避免把核心数据绑定在闭源平台导致日后"搬家"痛苦。来源：第3章

3. **Supabase 四大开箱即用模块**：数据库（PostgreSQL 中央档案室）、用户认证（Auth：邮箱/魔法链接/Google/GitHub 一键登录）、实时订阅（Realtime，WebSocket 推前端）、文件存储（Storage）。用积木式拼装，不要自己搭后端。来源：第3章

4. **安全下放到数据库层**：务必为所有表启用行级安全（RLS），策略是"用户只能操作 user_id 与自身认证 uid 匹配的记录"——这样即使绕过前端直接调 API，数据库也能阻止窥探他人数据。这是 Supabase 的核心安全特性。来源：第3章

5. **Vercel 当"部署总部"，CI/CD 白送**：与 GitHub 集成自动获得持续部署流水线（push→构建→测试→全球边缘网络上架）；边缘网络让用户就近访问、自动容灾、全球一致体验。别手动配服务器。来源：第3章

6. **域名是数字身份的战略投资，不是"一个网址"**：选"简短、易记、易拼、顺口"的域名，区分 SLD（自定义部分）与 TLD（.com 最受信任，业务相关可选 newgTLD 如 .ai/.app）；拥有专属域名提升信任、可配专业邮箱、防抢注、间接助 SEO。域名 ≠ URL（URL 含协议和路径）。来源：第3章

7. **子域名当"大房子的小房间"**：用 blog.example.com、shop.example.com 划分功能区域或搭开发/测试环境，不必买多个域名。来源：第3章

## 检查清单
- [ ] 选工具时是否先按"餐厅模型"定位它在全栈里的角色？
- [ ] 是否优先考虑开源/可自托管方案以避免供应商锁定？
- [ ] Supabase 是否用了"数据库/认证/实时/存储"开箱模块而非手写后端？
- [ ] 是否给所有表启用了 RLS（用户只能访问自己的记录）？
- [ ] 部署是否走了 Vercel+GitHub 的自动 CI/CD，而非手动运维？
- [ ] 域名是否简短易记、是否规划了子域名分工、DNS/SSL 是否配置到位？
