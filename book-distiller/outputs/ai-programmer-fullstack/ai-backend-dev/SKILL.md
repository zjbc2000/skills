# AI 后端开发与高级集成

## 何时使用
- 你有项目代码（SOLO 生成的或自己的），需要实现具体业务逻辑、修 bug、迭代。
- 你要做跨文件的大规模重构（如把 user 模型改名），或深度协作式调试。
- 你要让 AI 连接外部系统（GitHub、Figma、浏览器、数据库）执行真实任务。
- 你要判断该用"自主代理"还是"结对编辑器"处理当前任务。

## 核心规则

1. **SOLO 与 Cursor 分工：从0到1 vs 从1到N**：模糊想法、尚未定型 → 用 TRAE SOLO（架构师，快速生成整体框架，回答"做什么"）；已有代码、要精细实现 → 用 Cursor（工匠，精炼细节，回答"怎么做"）。二者不是谁更好，是开发流程不同阶段的工具。来源：第4章

2. **Cursor 的优势来自"项目地图"**：它是 AI 原生的代码编辑器（非插件），打开项目会为所有代码建语义索引。跨文件重构（改名连锁反应）、深度调试（给错误信息+日志追根溯源）之所以精准，都源于对全项目文件/函数/变量关联的理解。来源：第4章

3. **给 AI 结构化需求时用 `@` 命令增强准确率**：`@Web` 开启网络搜索获取最新信息，`useContext7` 启用 MCP 实时文档检索（从官方源拉取与当前技术栈/版本匹配的文档），减少过时 API 或虚构接口带来的错误。来源：第4章

4. **生成技术架构时直接给完整上下文**：明确技术栈（如 Next.js+Supabase+Stripe+Vercel）、核心需求（AI 功能/用户系统/计费系统）、并要求"生成详细架构方案 + 核心集成的前后端通信接口（含数据结构）"，AI 才会输出可落地的架构而非泛泛建议。来源：第4章

5. **用 MCP 把 AI 从"大脑"变成"助理"**：MCP（模型上下文协议，Anthropic 2024 提出）是 AI 与外部工具的统一标准，解决 N×M 连接器问题。它带来三大价值：减少幻觉（可查实时权威数据源）、解锁自动化（从"告诉你怎么做"到"直接帮你做"）、面向未来（行业开放标准）。来源：第4章

6. **MCP 理解用"餐厅比喻"**：主机（Host）=餐厅/AI 工具，客户端（Client）=服务员（承接你的指令），服务器（Server）=专业厨房（GitHub 厨房、Figma 厨房，各操作一个外部工具）。下单→服务员转达→厨房处理→回传给你。来源：第4章

7. **MCP 服务器去"应用商店"找**：MCP.so（社区市场，上万服务器）、Smithery.ai（企业级，7300+）、Awesome MCP Servers（GitHub 精选列表，分类+标注语言/系统）。像下载 App 一样给 AI 配工具。来源：第4章

## 检查清单
- [ ] 当前任务处于"从0到1"（→SOLO）还是"从1到N"（→Cursor）阶段，工具选对了吗？
- [ ] 要跨文件重构/深度调试时，是否用 Cursor 的"项目地图"能力而非逐文件手改？
- [ ] 生成架构/接口时是否给了完整技术栈+需求上下文，并用了 @Web / Context7 拉最新文档？
- [ ] 需要 AI 执行真实任务时，是否配置了 MCP 而非仅靠对话？
- [ ] 选 MCP 服务器时是否核实了来源（MCP.so / Smithery / Awesome 列表）？
